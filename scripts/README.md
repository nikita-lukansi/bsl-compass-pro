# scripts/ — реестр скриптов контура

Служебные скрипты BSL Compass Pro. Реестр фиксирует главное — **где
запускается скрипт** (хост или контейнер): `reindex.py` — только ВНУТРИ
контейнера, `export_docs.sh` и `measure_warm.py` — С ХОСТА. Структура
секций — cc-1c-skills-стиль (назначение / когда применять / команда /
примеры / границы): эти описания лягут в основу будущих скиллов.

| Скрипт | Где запускать | Назначение |
|---|---|---|
| `reindex.py` | в контейнере: `docker exec bsl-compass-pro python /app/scripts/reindex.py …` | ручное управление индексами в обход панели: пересборка, добавление конфигураций, векторизация, расширения |
| `measure_warm.py` | на хосте с маршрутом к Qdrant | контрольные замеры always_ram-переключения коллекции Qdrant |
| `export_docs.sh` | на хосте (Git Bash, из корня репо) | выгрузка корпуса справки ИТС из контейнера в DOCS_HUB-совместимый каталог |

## reindex.py — ручное управление индексами (ВНУТРИ контейнера)

**Назначение.** Постоянный обходной путь вместо панельных сборок: панельные
сборки крупных конфигураций гибнут по watchdog'у ядра (compass-96j). Конвейер —
как у ручного nohup-прогона: gyrfalcon build отвязанным воркером (лог
`/data/system/logs/reindex_<cid>_<ts>.log`, маркер `EXIT=<код>`) → тела методов
в FTS → отметка в реестре → прогрев int8/always_ram-коллекции Qdrant → JSON-отчёт
в stdout.

**Когда применять.** Пересборка индекса существующей конфигурации (особенно
КА-размера, methods > 400k); добавление новой конфигурации из хаба `/dumps`
в обход панели; фоновая векторизация уже собранной; регистрация расширения
в стеке активной конфигурации из CLI.

**Команды.**

```bash
docker exec bsl-compass-pro python /app/scripts/reindex.py reindex <cid> [--qdrant-stopped]
docker exec bsl-compass-pro python /app/scripts/reindex.py add <alias> \
    --from-dumps <папка_в_/dumps> [--vectorize --yes-vectorize] [--qdrant-stopped]
docker exec bsl-compass-pro python /app/scripts/reindex.py vectorize <cid> \
    --yes-vectorize [--wait-warm [сек]]
docker exec bsl-compass-pro python /app/scripts/reindex.py ext-add <Имя> \
    --position <N> --purpose <Исправление|Адаптация|Дополнение> [--source hub|<путь>]
```

- `reindex <cid>` — пересобрать индекс; `--qdrant-stopped` — подтверждение,
  что владелец сам остановил qdrant (обязателен для КА-размера, «правило
  памяти»: воркер сборки ~3.5 ГиБ + qdrant ~2 ГиБ не влезают в лимит ВМ);
- `add <alias> --from-dumps …` — полный путь новой конфигурации: регистрация
  в реестре + копирование выгрузки в `/data/configs/<cid>/source` + сборка;
  `--vectorize --yes-vectorize` — после сборки запустить отвязанный воркер
  эмбеддингов (двойное подтверждение: платный внешний API);
- `vectorize <cid> --yes-vectorize` — векторизация без пересборки; `--wait-warm
  [сек]` — поллинг финала воркера (без значения — потолок 3600 с), по умолчанию
  не ждётся;
- `ext-add <Имя> --position <N> --purpose <…> [--source hub|<путь>]` — CLI-обёртка
  агентского тура `extension_add`; индекс НЕ пересобирает (подсказка в отчёте).

**Границы.** Не запускать параллельно с панельной сборкой (общая память
контейнера); `--stop-qdrant` сам qdrant не останавливает (docker CLI в образе
нет) — печатает подсказку; векторизация платная (оценка ≈ методы × 11 токенов).
Полный текст — `README.md`, раздел «Управление индексами вручную».

## measure_warm.py — замеры always_ram-переключения Qdrant (на хосте)

**Назначение.** Контрольные замеры переключения `always_ram` int8-квантизации
на живой коллекции (compass-fa9): длительность выгрузки RAM-копии, длительность
прогрева, латентность поиска сразу после прогрева и серией после.

**Когда применять.** Диагностика производительности семантического поиска
(холодные запросы, таймауты) и проверка прогрева при `config_use`/повторном
включении векторов. Начальное состояние `always_ram` возвращается по
завершении — полигон не меняется.

**Команда.**

```bash
python scripts/measure_warm.py --url http://qdrant:6333 \
    --collection cfg_Compass_KA_798247c2_code --repeats 3
```

`--url` — Qdrant, доступный с места запуска (в compose хостового порта у qdrant
нет: имя `qdrant` резолвится в сети контейнеров); `--repeats` — число замеров
латентности.

**Как читать результат.** JSON: `points`/`dim` — размер коллекции;
`timings_sec.evict_false_sec` — выгрузка RAM-копии; `warm_true_sec` — прогрев;
`query_after_warm_sec` — серия латентностей после прогрева; `restore_sec` —
возврат исходного состояния (если коллекция исходно была холодной). Размер
на диске API не отдаёт — снимать вручную (`du` по volume).

## export_docs.sh — выгрузка корпуса справки (на хосте)

**Назначение.** Снимок корпуса документации ИТС конфигурации из контейнера
в DOCS_HUB-совместимый каталог на хосте: перенос между машинами/контурами
и приём через `help_import` без ИТС-кредов (машина с ИТС-доступом выгрузила —
остальные импортировали).

**Когда применять.** Передача корпуса справки на другую машину или во второй
инстанс; бэкап корпуса перед `help_sync`; питание хаба `DOCS_HUB`
(`./docs-dumps`) для `help_import`.

**Команда** (Git Bash, из корня репо; подробности — `scripts/export_docs.sh --help`):

```bash
scripts/export_docs.sh                                   # активная конфигурация → ./docs-dumps/<source_id>
scripts/export_docs.sh Compass_KA_798247c2               # конкретная
scripts/export_docs.sh Compass_KA_798247c2 /d/tmp/kadoc  # в свой каталог
scripts/export_docs.sh --all ../backups/docs             # все корпуса с /data/docs/
```

**Границы.** Хостовой скрипт — контейнер `bsl-compass-pro` должен быть запущен;
корпус только читается (`docker exec ls` + `docker cp`), ничего не мутирует;
существующий dest не перезаписывается молча — отказ без `--force`; для узнавания
активной конфигурации нужен `python` в PATH (парсинг `/api/status`; jq не нужен).
Активная конфигурация может не иметь корпуса — тогда честный отказ с подсказкой,
какие конфигурации корпус имеют.
