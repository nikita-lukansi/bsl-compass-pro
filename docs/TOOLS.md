# Справочник инструментов (MCP-тулы)

Что вызывает каждый тул, что возвращает и где границы — открывай, когда
сомневаешься, чем отвечать.

Нативный справочник тулов MCP-сервера compass-pro для агентов: какой тул,
когда и как. Все примеры сверены живыми вызовами на рабочем контуре
(КА 2.5.22, 653 756 методов, 2026-11-16); примеры мутаций (пересборки,
стек расширений, офлайн-задачи) описаны по докстрингам и исходникам —
живьём они не выполнялись, чтобы не менять состояние рабочего контура.

Стратегия и маршруты изучения конфигурации — отдельная методичка:
[EXPLORATION.md](EXPLORATION.md). Здесь — справочник: что вызывает, что
возвращает.

## Честные границы (читать первым)

- Вердикты оракулов трёхзначны: `holds: true` — доказано (есть evidence),
  `holds: false` — доказано «нет», `holds: null` — неизвестно
  (`not_indexed` / `object_not_found`). `None` ≠ `False`: отрицательный
  вердикт недоказуем, когда объект индексирован частично.
- `_no_matches` — честное «ничего не найдено», не ошибка. Тот же запрос
  без изменений не ретраить — переформулировать (формы слов, корни,
  префикс `*`).
- `error` — контур не готов (нет индекса/конфигурации/рантайма); в `hint`
  — путь выхода.
- Field-вердикты несут `config` (активная конфигурация): перед
  рассуждением проверь, что это та база, о которой спрашиваешь.
- Индекс хранит имена объектов **без** вида («ВидыЗапасов», не
  «Справочник.ВидыЗапасов»); имя с видом принимается и уточняет вид
  («ПланСчетов.Хозрасчетный»). Одно имя у разных видов метаданных —
  честная дизамбигуация `_ambiguous` со списком категорий.
- Тела методов участвуют в FTS-поиске (`code_grep`) после ПОЛНОЙ сборки
  (пост-шаг заливки тел); тел в индексе нет — именной FTS по именам,
  по телам regex-обходом `source_grep`, по смыслу — `codesearch`,
  одиночный метод — `read_function`.

## 1. Разведка метаданных

### `verify_field(object_name, field)`
- **Назначение:** оракул «у объекта есть реквизит / ТЧ / колонка ТЧ».
- **Когда:** перед любым утверждением о реквизите; проверка фактов из
  задачи/расширения.
- **Параметры:** `field` — «Имя» (шапка или колонка ТЧ, если имя
  уникально) или «ТЧ.Колонка» (конкретная секция); имя объекта — с видом
  или без.
- **Вердикты:** `true` + `evidence` (тип, секция, синоним); `false`
  `field_not_found` + `nearest` (похожие имена) — только когда секции ТЧ
  индексированы; `null` `not_indexed` (секции ТЧ не в индексе — например
  ВидыСубконто планов счетов) или `object_not_found`.
- **Пример:** `verify_field("Документ.ПриобретениеТоваровУслуг",
  "Товары.Сумма")` → `holds: true`, evidence `ts_name: Товары,
  columns_in_section: 39`, `config: KA`. Честный None:
  `verify_field("ПланСчетов.Хозрасчетный", "ВидыСубконто")` →
  `holds: null, verdict: "not_indexed"` — «отрицательный вердикт
  недоказуем».
- **Связанные:** `check_claims` (батч), `object_overview`,
  `predefined_details`, `records`/`data_query` (живая база).

### `check_claims(claims)`
- **Назначение:** батч-оракул — пачка утверждений одним вызовом.
- **Когда:** сверка контракта расширения, массовая проверка фактов
  (боевой замер: 61 claim за 3 вызова).
- **Параметры:** список `{kind: "field", object, field}` или
  `{kind: "call", caller, callee}`.
- **Вердикты:** на каждый элемент — как у `verify_field`/`verify_call`
  (+`config`); кривой элемент — `invalid_claim` (`holds: null`), пачку
  не роняет; сводка `holds_true/false/unknown`.
- **Пример:** батч из field-клейма «Товары.Сумма» (→ true) и call-клейма
  «ПровестиИСформироватьДвижения → ОбработкаПроведения» (→ false,
  «прямого ребра нет»).
- **Связанные:** `verify_field`, `verify_call`.

### `object_overview(object_name)`
- **Назначение:** всё по объекту одним вызовом: реквизиты с видами
  (измерение/ресурс/…), ТЧ с колонками, подсистемы, формы, значения
  перечислений, движения, топ-методы, ссылки на объект.
- **Когда:** стартовая точка по объекту; замена чтения XML-выгрузки.
- **Параметры:** имя (с видом — точнее; без вида при неоднозначности —
  `_ambiguous`).
- **Вердикты:** `attributes_total` + `attributes_note` при усечении
  (>50); `table_sections` — ТЧ с колонками; `_no_matches` — объекта нет.
- **Пример:** `object_overview("РегистрНакопления.ТоварыКОформлениюДокументовИмпорта")`
  → 13 атрибутов (`ДокументПоступления: DocumentRef.ПриобретениеТоваровУслуг`,
  `НомерГТД`), подсистемы `ОбъектыМеждународные/ОбъектыУТКАУП`, формы,
  топ-методы.
- **Связанные:** `verify_field` (точность), `repomap`, `who_touches`,
  `predefined_items`.

### `predefined_items(object_name, query="", limit=100)`
- **Назначение:** предопределённые элементы (справочники/планы) и
  ЗНАЧЕНИЯ перечислений из индекса.
- **Когда:** сверка состава перечислений/планов; поиск по подстроке.
- **Параметры:** `query` — подстрока имени/кода/синонима
  (регистронезависимо); `limit` (0 — без лимита, есть честный
  `_truncated`).
- **Вердикты:** перечисления → `{items, kind: "enum_values", total}`
  (синонимов значений индекс не хранит); пусто `[]` — честно: у объекта
  нет предопределённых (Predefined.xml в выгрузке отсутствует).
- **Пример:** `predefined_items("Перечисление.ХозяйственныеОперации",
  query="Закупка")` → 18 значений (`ЗакупкаПоИмпорту`, …); поймал
  P0-дефект расширения «ЮрАдресКонтрагента» vs
  «ЮридическийАдресКонтрагента» в боевой сессии.
- **Связанные:** `predefined_details` (все поля + ТЧ из выгрузки),
  `verify_field`.

### `predefined_details(object_name)`
- **Назначение:** предопределённые элементы из Predefined.xml выгрузки —
  все поля, включая ТЧ; нужен source_root.
- **Когда:** когда `predefined_items` мало (имя/код), нужны полные
  данные элемента.
- **Вердикты:** честный `error` «Predefined.xml не найден» со списком
  пройденных путей — объект без предопределённых (наполнение данными).
- **Пример:** `predefined_details("Справочник.ВидыЗапасов")` → error
  (ВидыЗапасов наполняются данными — корректный отказ); для планов
  счетов — `account_subaccounts`.
- **Связанные:** `predefined_items`, `account_subaccounts`.

### `account_subaccounts(plan_name, code)`
- **Назначение:** субконто предопределённого счёта плана счетов.
- **Когда:** структура счёта (бухучёт) — «какие виды субконто у 41».
- **Пример:** `account_subaccounts("Хозрасчетный", "41")` → счёт
  «Товары», тип «Активный», `extra` (OffBalance, Order); если ТЧ
  субконто в файле не нашлась — честная `note` + `tables_found`.
- **Связанные:** `predefined_details`.

### `list_objects(category="", subsystem="", search="", limit=100)`
- **Назначение:** каталог объектов с синонимами: фильтры по категории,
  подсистеме, поиску.
- **Когда:** карта подсистемы по корню слова; ответ «где включить» —
  поиск по корню отдаёт и константы, и функциональные опции.
- **Параметры:** `search` — FTS trigram (≥3 символов; короче — LIKE);
  `category` («Documents», «Catalogs»…), `subsystem`.
- **Пример:** `list_objects(search="импорт")` → 56 объектов всех видов:
  регистр, документы, справочники, общие модули… и константы-опции
  (`ИспользоватьИмпортныеЗакупки`) — карта подсистемы за один вызов.
- **Связанные:** `subsystems_overview`, `subsystems_of`,
  `object_overview`.

### `subsystems_overview()`
- **Назначение:** обзор подсистем: имена + число объектов, топ-100.
- **Когда:** с чего начать в незнакомой конфигурации — крупные
  подсистемы первыми.
- **Связанные:** `list_objects(subsystem=…)`, `subsystems_of`.

### `subsystems_of(object_name)`
- **Назначение:** в каких подсистемах состоит объект.
- **Вердикты:** `_no_matches` + подсказка — прямого вхождения нет
  (объект-сирота?).
- **Пример:** `subsystems_of("Документ.ТаможеннаяДекларацияИмпорт")` →
  `Закупки`, `ОбъектыМеждународные`, `ОбъектыУТКАУП`.
- **Связанные:** `object_overview` (подсистемы внутри ответа).

### `object_rights(object_name)`
- **Назначение:** права ролей на объект (Rights.xml).
- **Когда:** вопросы доступа/RLS, чек «роль видит объект».
- **Связанные:** `triggers_on_write` (подписки с ограничением доступа).

### `find_in_forms(what, object_name=None, limit=30)`
- **Назначение:** элементы/обработчики в формах: что и где на форме.
- **Когда:** найти, где на форме живёт опция/реквизит и её обработчик.
- **Пример:** `find_in_forms("ИспользоватьИмпортныеЗакупки")` → флажок в
  формах «УчетНДСИмпортЭкспорт» панели администрирования, обработчик
  `ИспользоватьИмпортныеЗакупкиПриИзменении`.
- **Связанные:** `read_module` (тело формы), `entry_points`.

### `find_references_to(object_name, limit=100)`
- **Назначение:** кто ссылается на объект в метаданных (типы реквизитов,
  состав планов обмена, права, подсистемы).
- **Когда:** «что сломается при изменении объекта», влияние по
  метаданным.
- **Пример:** `find_references_to("Документ.ТаможеннаяДекларацияИмпорт")`
  → тип атрибута «ВладелецФайла» у присоединённых файлов, реквизиты
  «РасчетныйДокумент» у сверок взаиморасчетов.
- **Связанные:** `who_touches` (использования в коде), `who_creates`.

## 2. Графы и код

### `read_function(name, module_hint=None, include_body=True)`
- **Назначение:** метод одним вызовом: сигнатура + тело + callees +
  callers (+бейдж перехватов расширениями).
- **Когда:** «как сделано» в конкретном методе; кто вызывает и что
  вызывает.
- **Параметры:** `module_hint` — уточнение модуля, русский вид
  принимается: «Документ.X» → «Documents/X», «РегистрНакопления.Y» →
  «AccumulationRegisters/Y»; `include_body=false` — без тела (экономия).
- **Вердикты:** `error` «метод не найден»; `ambiguous_total` >1 — имя
  неуникально, смотрите `module_path`.
- **Пример:** `read_function("ЗаполнитьТовары",
  module_hint="РегистрНакопления.ТоварыКОформлениюДокументовИмпорта",
  include_body=false)` → метод найден в модуле формы «ПодборПоОстаткам»,
  callees/callers + `ambiguous_total: 1`.
- **Связанные:** `search_function` (найти имя), `read_module`
  (структура), `call_paths`, `effective_method` (перехваты).

### `read_module(object_name, module_hint="", include_body=false, line_start=0, line_end=0)`
- **Назначение:** модуль целиком: путь, заголовок, области, методы с
  границами строк.
- **Когда:** обзор модуля перед точечным `read_function`; у объекта
  несколько модулей (Объект/Менеджер/Формы) — без `module_hint`
  возвращаются все.
- **Вердикты:** `error` + hint «проверьте имя (search_function) или
  module_hint»; тело читается только для ОДНОГО модуля за вызов.
- **Пример:** `read_module("Документ.ТаможеннаяДекларацияИмпорт",
  module_hint="ObjectModule")` → 12 методов по областям
  (ПрограммныйИнтерфейс / ОбработчикиСобытий / Служебные…), границы
  строк.
- **Связанные:** `read_function` (тело метода), `source_grep` (тела
  всех модулей).

### `repomap(object_name, top=20)`
- **Назначение:** карта объекта — топ-методы по локальной центральности
  (PageRank в подграфе объекта).
- **Когда:** «сердце» объекта: с каких методов начинать чтение.
- **Вердикты:** `_no_matches` — методов объекта нет; `outside: true` —
  метод вне объекта (БСП-хелпер в графе).
- **Пример:** `repomap("ТоварыКОформлениюДокументовИмпорта", top=5)` →
  верхушка: `ЗаполнитьТовары` (score 1.0), `ПоместитьВХранилище`,
  БСП-хелпер `ЭлементыКоллекции` (outside).
- **Связанные:** `object_overview.top_methods` (по размеру, не по
  графу), `call_paths`.

### `call_paths(method, direction="down", depth=10, module_hint=None, target=None)`
- **Назначение:** дерево вызовов по рёбрам calls; `target` — поиск
  кратчайшего пути до метода (BFS).
- **Когда:** «доходит ли вызов от A до B»; обзор кто-кого-вызывает на N
  уровней.
- **Параметры:** `direction`: down (кого вызывает) / up (кто вызывает);
  `depth` 1..50; бюджет 500 узлов → честный `_truncated`.
- **Вердикты:** неоднозначный старт — отказ со списком кандидатов и
  хинтом `module_hint`; `unresolved: true` — вызов не разрешён в метод
  индекса (платформенный); `cycle: true` — цикл в графе.
- **Пример:** `call_paths("ЗаполнитьТовары",
  module_hint="РегистрНакопления.ТоварыКОформлениюДокументовИмпорта",
  depth=3)` → дерево 70 узлов; платформенные вызовы — листья
  `unresolved`.
- **Связанные:** `verify_call` (одно ребро — оракул), `read_function`
  (callers/callees плоско).

### `who_creates(object_name, limit=50)`
- **Назначение:** кто создаёт объект программно: платформенные
  СоздатьДокумент/СоздатьЭлемент/СоздатьНаборЗаписей + create-usages +
  ссылки метаданных.
- **Когда:** «откуда берутся документы этого вида».
- **Вердикты:** `_no_matches` — честно (созданий платформенными
  методами не найдено; помечать хвост «недоказано»).
- **Пример:** `who_creates("Документ.ТаможеннаяДекларацияИмпорт")` →
  `_no_matches` — в коде не создаётся (вводится вручную).
- **Связанные:** `who_touches`, `find_references_to`.

### `who_touches(object_name, limit=50)`
- **Назначение:** data-lineage: кто читает/пишет данные объекта в коде
  (по code_usages) + регистраторы (если объект — регистр).
- **Когда:** самая ценная страница по регистру: все регистраторы +
  читатели одним вызовом (боевой вывод).
- **Вердикты:** `_no_matches` + hint — обращений не найдено.
- **Пример:** `who_touches("РегистрНакопления.ТоварыКОформлениюДокументовИмпорта")`
  → запросы в RecordSetModule/формах + 15 регистраторов
  (`ПриобретениеТоваровУслуг`, `ТаможеннаяДекларацияИмпорт`, …).
- **Связанные:** `who_creates`, `find_references_to`,
  `document_movements` (фактические движения живого документа).

### `verify_call(caller, callee)`
- **Назначение:** оракул «caller вызывает callee» по рёбрам графа.
- **Когда:** проверка одного утверждения о вызове; в батче —
  `check_claims`.
- **Вердикты:** `true` + evidence (файл, resolution, confidence);
  `false` «прямого ребра нет» — не ошибка, а доказанное отсутствие.
- **Пример:** `verify_call("ПриСозданииНаСервере", "ЗаполнитьТовары")`
  → true, evidence: форма «ПодборПоОстаткам», resolution local.
- **Связанные:** `check_claims` (батч), `call_paths` (путь целиком).

### `triggers_on_write(object_name)`
- **Назначение:** что срабатывает при записи: обработчики объекта +
  подписки на события + движения по регистрам (+бейдж перехватов).
- **Когда:** планирование доработки записи/проведения; «куда встать».
- **Вердикты:** `handlers` (по модулям, с строками), `subscriptions`
  (может быть объёмным — БСП-подписки перечисляют типы источников),
  `movements`.
- **Пример:** `triggers_on_write("Документ.ТаможеннаяДекларацияИмпорт")`
  → ПередЗаписью/ПриЗаписи/ОбработкаПроведения/… в ObjectModule с
  границами строк + подписки БСП.
- **Связанные:** `read_module` (тело модуля), `effective_method`.

### `who_overrides(method, module_hint=None, include_dev=false)`
- **Назначение:** все перехваты метода по стеку расширений: аннотация
  (kind), расширение, effective_position, active/shadowed для «Вместо».
- **Когда:** «метод расширяется? кем? кто активен?» — перед правкой
  типового метода.
- **Вердикты:** `_no_matches` — цель не расширяется; dev-расширения
  скрыты с `dev_hidden=N` (include_dev=true — показать); порядок
  подтверждён — `order_confirmed`.
- **Пример:** на КА без расширений:
  `who_overrides("ОбработкаПроведения")` → `_no_matches` (честно).
- **Связанные:** `effective_method` (итоговый поток), `extension_stack`.

### `entry_points()`
- **Назначение:** точки входа конфигурации: регламентные задания
  (ScheduledJobs) с методами-обработчиками.
- **Когда:** «что запускается само по расписанию», где живут фоновые
  процессы.
- **Связанные:** `read_function` по handler_procedure.

### `get_skd_info(template_path)`
- **Назначение:** схема СКД по пути (относительный — от source_root
  активной конфигурации): наборы данных, поля, параметры, вычисляемые
  поля.
- **Когда:** разбор отчёта без конфигуратора.
- **Вердикты:** `error` «файл не найден / не является схемой СКД».
- **Пример:** `get_skd_info("Reports/ИмпортныеТоварыКОформлению/Templates/ОсновнаяСхемаКомпоновкиДанных/Ext/Template.xml")`
  → набор данных `ТоварыКОформлению` (kind: object) + путь.
- **Связанные:** `read_module` (модуль отчёта), `find_in_forms`.

## 3. Поиск

### `search_function(query, limit=10)`
- **Назначение:** поиск методов по имени (FTS по methods).
- **Когда:** старт «где живёт метод с таким именем»; перед
  `read_function` при неоднозначных именах.
- **Пример:** `search_function("ЗаполнитьТовары")` → 5+ одноимённых
  методов в разных модулях с путями и границами строк — выбирай по
  `rel_path`.
- **Связанные:** `code_grep` (по коду и именам со сниппетами),
  `read_function`.

### `code_grep(query, limit=20, module_hint=None)`
- **Назначение:** полнотекстовый поиск по коду — тела методов залиты в
  индекс пост-шагом сборки (methods_bodies_fts); тел нет —
  именной FTS-маршрут по methods_fts (только name, ddl.rs v0.1.20).
- **Когда:** токены кода («Возврат», «ПровестиЛогику», «ЗначениеЗаполнено»)
  и имена — строка объявления входит в тело; слова = И, «часть*» —
  префикс, кавычки — фраза. Токенизация unicode61 — по словам:
  CamelCase-идентификатор цельный токен, подстрока внутри него —
  `source_grep`.
- **Вердикты:** тела есть → `{bodies_indexed: true, results: [...]}`
  со сниппетом-подсветкой; тел нет → именные запросы ищутся по name,
  для паттернов с код-символами — честный `bodies_indexed: false` с
  подсказками (search_function / source_grep / codesearch); невалидный
  FTS5-запрос — честный error с синтаксисом.
- **Условия работы:** тела появляются после ПОЛНОЙ сборки (пост-шаг);
  инкремент перезаливает только изменённые модули (новые файлы — после
  полной). `COMPASS_BODIES_FTS=off` отключает слой целиком.
- **Пример:** `code_grep("ЗначениеЗаполнено")` → методы с вызовом в теле
  + сниппет строки вызова; `code_grep("Таможенн*", limit=3)` → по именам.
- **Связанные:** `source_grep` (regex по телам, вне индекса),
  `codesearch` (по смыслу), `search_function` (имена).

### `source_grep(pattern, module_hint=None, limit=20, context_lines=2, ignorecase=false)`
- **Назначение:** regex/литеральный поиск по ТЕЛАМ модулей — полный
  обход source_root (*.bsl), вне индекса.
- **Когда:** то, чего нет в индексе и доке: условия в телах, литералы,
  вызовы конкретных строк. ЭТО ТУЛ закрывает «ручной grep по дампу» —
  агенту ходить в дамп руками не нужно.
- **Параметры:** `pattern` — Python regex до 200 символов (литерал —
  экранируй точки); `module_hint` — подстрока пути (сужает обход);
  `context_lines` 0..5.
- **Вердикты:** `matches` (файл, строка, контекст), `files_total` /
  `files_scanned`, `truncated` — честный при дедлайне (SOURCE_GREP_TIMEOUT,
  сек., дефолт 30) и при лимите; `config` в ответе.
- **Пример:** `source_grep("НомерГТД", module_hint="УчетИмпорта",
  limit=3)` → строка запроса в CommonModules/УчетИмпорта/Ext/Module.bsl:471
  с контекстом. Пустой результат — тоже честный (files_scanned даёт
  объём просмотра).
- **Связанные:** `read_function`/`read_module` (тело конкретного
  метода/модуля), `code_grep` (имена).

### `codesearch(query, limit=10)`
- **Назначение:** семантический поиск по методам: вектор + буквальный
  через RRF по карточкам (имя, параметры, тип модуля, объект).
- **Когда:** «найти методы, делающие X» без знания имён.
- **Условия работы:** собран структурный индекс + настроена семантика
  (EMBEDDING_*) + конфигурация векторизована (`points > 0`).
- **Вердикты:** «векторный индекс пуст» → запусти векторизацию (тул
  `start_semantic_index` или кнопка панели), запрос НЕ ретраить;
  «Qdrant не ответил» — сбой сервера отличим от пустого индекса,
  тоже не ретраить вслепую.
- **Связанные:** `semantic_status` (points/warm_state),
  `start_semantic_index`, `code_grep`/`source_grep`.

## 4. Документация (ИТС + справка конфигурации)

### `help_status()`
- **Назначение:** состояние корпуса документации: источники
  (source_id → страниц/символов), креды (без секрета), идёт ли выгрузка.
- **Когда:** перед `help_search` — что есть в корпусе; боевой контур:
  ka25doc 3 334 стр. + primary (справка выгрузки) 5 396 стр.
- **Связанные:** `help_search`, `help_sync`, `help_import`.

### `help_search(query, limit=10, source_id=None)`
- **Назначение:** полнотекстовый поиск по доке (FTS5: title /
  object_name / text) с `mentions` — именами объектов индекса,
  встретившимися в тексте.
- **Когда:** «как должно работать» до архитектуры; mentions — мост
  «дока ↔ код» (дальше `verify_field`/`read_function`).
- **Вердикты:** `_no_matches` + hint про формы слов: FTS5 не знает форм
  («серии» ≠ «серия») — ищи по корням с префиксом «парти*»; кривой
  FTS-синтаксис → честное `_no_matches` с той же подсказкой.
- **Пример:** `help_search("импорт и таможенная декларац*")` → страницы
  «Таможенная декларация на импорт» из обоих источников; mentions:
  `ТаможеннаяДекларацияИмпорт`, `ПриобретениеТоваровУслуг`, `УчетНДС`.
- **Связанные:** `help_read` (страница целиком), `list_objects`
  (лексика для запроса), `source_grep` («как сделано»).

### `help_read(source_id, path)`
- **Назначение:** страница документации целиком (source_id + path из
  `help_search`), text очищен от навигации ИТС; mentions прилагаются.
- **Когда:** привести evidence о штатном поведении; прочитать раздел.
- **Связанные:** `help_search`, `verify_field`.

### `help_import(source_id, cid="")`
- **Назначение:** приём ГОТОВОГО корпуса из хаба DOCS_HUB без ИТС-кредов
  (копия в дом конфигурации + kb sync); сеть не трогается.
- **Когда:** корпус выгружен на другой машине; перенос между машинами.
- **Вердикты:** честные отказы — корпуса нет в хабе, дом занят, идёт
  сборка (kb sync пишет в тот же index.db).
- **Связанные:** `help_status`, `help_sync`.

### `help_sync(source_id="ka25doc")`
- **Назначение:** выгрузить/обновить корпус ИТС с its.1c.ru (логин →
  оглавление → файлы → kb sync), фоном.
- **Когда:** первичное наполнение/обновление; нужны креды ИТС
  (ITS_LOGIN/ITS_PASSWORD или ITS_COOKIE) — иначе честный отказ
  (поиск/чтение по уже выгруженному корпусу работают).
- **Связанные:** `help_status` (прогресс), `help_sync_pause` /
  `help_sync_resume` (пауза оператора — сеть молчит), `help_remove`.

### `help_remove(source_id="ka25doc")`
- **Назначение:** отвязать help-источник от индекса (remedy: смена
  выгрузки, пересборка корпуса с нуля). Файлы на диске не удаляются.
- **Связанные:** `help_sync`, `help_import`.

### `help_sync_pause()` / `help_sync_resume()`
- **Назначение:** пауза/продолжение выгрузки корпуса: клиент замирает
  перед следующим запросом (сеть молчит, деньги не тратятся).
- **Вердикты:** пауза вне прогона — честное info «выгрузка не идёт».

## 5. Живые данные (обработка «КомпасРантайм», только чтение)

Общая механика: два режима — онлайн (RUNTIME_URL, HTTP) и офлайн
(RUNTIME_MODE=offline: файловый обмен queue/req_*.json → форма «Обмен» →
results/resp_*.json). В офлайн-режиме одиночные вызовы НЕ формируются —
каждый вернёт честный info-гард «соберите пакет offline_submit([...])».
Состояние контура — `runtime_status`. База открывается под пользователем
«только чтение», RLS действует.

### `runtime_status()`
- **Назначение:** состояние рантайм-контура: режим, подключение, очереди
  офлайн-обмена.
- **Пример:** офлайн-режим → `{mode: "offline", pending_requests: 0,
  ready_responses: 0}`; онлайн без RUNTIME_URL → честный hint с обоими
  путями включения.
- **Связанные:** `offline_submit`/`offline_wait` (офлайн-конвейер).

### `data_query(query, limit=10, params=None)`
- **Назначение:** SELECT к живой базе (только чтение); параметры —
  `&Имя: значение`.
- **Контракт лимита:** если в запросе нет своего ПЕРВЫЕ/TOP, обработка
  вставляет «ПЕРВЫЕ N+1» (N = limit; строка N+1 — служебная, в ответ не
  попадает). Свой ПЕРВЫЕ/TOP исполняется как написан.
- **Вердикты:** офлайн → info-гард с рецептом offline_submit; эхо
  запроса в ошибках — исполненный текст с инжекцией лимита.
- **Пример (офлайн):** `data_query("ВЫБРАТЬ Ссылка, Наименование ИЗ
  Справочник.Организации", limit=3)` → `{info: "офлайн-режим:
  одиночный вызов не формируется — соберите пакет через
  offline_submit([...]) и дождитесь offline_wait(task_id)"}`.
- **Связанные:** `records` (универсальная выборка), `get_object`.

### `records(Объект, Поля, Отборы, Порядок, Лимит=100, Курсор, Виртуальная, ПараметрыВТ)`
- **Назначение:** универсальная выборка записей ЛЮБОГО вида метаданных
  с keyset-курсором.
- **Когда:** данные сущности с фильтрами/порядком; страницы через
  `Курсор` (opaque-продолжение из ответа).
- **Параметры:** `Объект` — «Вид.Имя» как в языке запросов; `Отборы` —
  `[{Поле, Операция, Значение}]`, операции eq/ne/gt/ge/lt/le/contains/
  inList/isNull/isNotNull; `Виртуальная` — «Остатки»|«Обороты»|
  «СрезПоследних» для регистров; `ПараметрыВТ` — `{Период|НачалоПериода|
  КонецПериода: ГГГГММДДЧЧММСС}`; `Лимит` — потолок 1000.
- **Пример (из докстринга):** `records("РегистрНакопления.Продажи",
  Поля=["Период", "Регистратор", "Количество"],
  Отборы=[{"Поле": "Период", "Операция": "ge",
  "Значение": "20260101000000"}], Порядок=[{"Поле": "Период",
  "Направление": "убыв"}], Лимит=200)`.
- **Связанные:** `data_query` (произвольный SELECT), `register_records`.

### `get_object(type_name, name, key, key_kind="код")`
- **Назначение:** объект базы по ключу: реквизиты, ТЧ (первые строки),
  пометка проведения. `key_kind`: код | наименование | гуид.
- **Пример (из докстринга):** `get_object("Справочник", "Контрагенты",
  "000000001")`.
- **Связанные:** `catalog_samples` (как заполняют), `records`.

### `register_records(register_name, limit=10)`
- **Назначение:** срез первых N записей регистра (проводки/сведения).
- **Пример (из докстринга):** `register_records("Продажи")`.
- **Связанные:** `records`, `document_movements`.

### `catalog_samples(catalog_name, limit=5)`
- **Назначение:** как заполняются элементы справочника: первые N
  элементов со всеми реквизитами — паттерны наполнения живой базы.
- **Пример (из докстринга):** `catalog_samples("Номенклатура", 5)`.
- **Связанные:** `get_object`.

### `document_movements(ТипОбъекта, Имя, Ключ, ВидКлюча="код", ЛимитНаРегистр=10)`
- **Назначение:** движения одного документа по всем регистрам: обзор
  количества по регистрам (только непустые) + строки движений.
- **Пример (из докстринга):** `document_movements("Документ",
  "РеализацияТоваровУслуг", "00-000001")`.
- **Связанные:** `who_touches` (потенциальные регистраторы по индексу),
  `records`.

### `event_log(НачалоПериода, КонецПериода, Объект="", Пользователь="", Событие="", Лимит=100)`
- **Назначение:** записи журнала регистрации за период (окно ≤ 31 дня,
  ГГГГММДДЧЧММСС), сортировка по времени убыв; пагинация — сузить
  период по дате первой строки.
- **Пример (из докстринга):** `event_log("20261101000000",
  "20261112120000", Событие="Данные.Проведение")`.
- **Связанные:** `records`, `document_movements`.

### `offline_submit(calls, description="")` / `offline_wait(task_id, timeout=120)`
- **Назначение:** офлайн-конвейер: агент НЕ пишет файлы сам — шлёт
  вызовы `[{method, params}]`, компас собирает пакет (токены ссылок
  подставляет ядро), 1С забирает формой «Обмен»; затем
  `offline_wait(task_id)`.
- **Параметры:** `timeout` ≤ 120 с (длинный вызов может оборвать
  MCP-клиент); повторный вызов идемпотентен.
- **Вердикты:** обе дорожки перекрыты (онлайн без RUNTIME_URL и офлайн
  выключен) — честный тупик с путями выхода.
- **Пример (из докстринга):** `offline_submit([{"method": "data_query",
  "params": {"query": "ВЫБРАТЬ ПЕРВЫЕ 10 * ИЗ Справочник.Контрагенты"}}],
  "остатки по контрагенту")` → `{task_id, status, calls}`.
- **Связанные:** `runtime_status`, `offline_task_status`,
  `offline_deanonymize`.

### `offline_task_status(task_id)`
- **Назначение:** лёгкий статус офлайн-задачи по id БЕЗ блокировки:
  статус, переходы, наличие результата.
- **Когда:** проверить, пришёл ли ответ 1С, не вися в `offline_wait`
  (короткий цикл ожидания может оборвать MCP-клиент).
- **Вердикты:** результаты-токены НЕ возвращаются — за ними
  `offline_wait(task_id)` (идемпотентен, выдаст их повторно); задача
  другого чата/неизвестный id — честный отказ + живые задачи своего чата.
- **Связанные:** `offline_submit`/`offline_wait`, `runtime_status`.

### `offline_deanonymize(text)`
- **Назначение:** токены обезличивания в тексте → исходные значения
  (проверка кода агентом; деанонимизация только локально, не в базу).
- **Пример:** `offline_deanonymize("Токен Контрагент_Т1 в тексте")` → без
  словаря чата текст возвращается как есть.
- **Связанные:** `offline_submit` (токены подставляются в пакет ядром).

## 6. Расширения

Порядок применения слоёв задаёт (назначение, позиция в списке
конфигуратора); платформа эти факты в файлах выгрузки НЕ хранит —
`extension_add` без них не выполняется, а возвращает подсказку спросить
разработчика. Активный «Вместо» — верхний слой по effective_position;
«Перед» исполняются по УБЫВАНИЮ позиции, «После» — по ВОЗРАСТАНИЮ.

### `extension_stack()`
- **Назначение:** стек активной конфигурации: эффективный порядок +
  счётчики из индекса + сверка имён (в индексе, но не в стеке →
  предупреждение «добавьте через extension_add»).
- **Пример:** на КА без расширений → `{stack: [], extensions: [],
  order_confirmed: false, warnings: []}`.
- **Связанные:** `extension_map`, `who_overrides`, `effective_method`.

### `extension_map(object_name=None)`
- **Назначение:** без параметра — обзор (что заимствовано/перехвачено,
  effective_position/purpose); с объектом — что типовое, что добавлено,
  что переопределено (для «Вместо» — active/shadowed).
- **Вердикты:** без стека поля порядка не добавляются, сверху
  `order_confirmed: false`; `_no_matches` — объект в расширениях не
  найден.
- **Связанные:** `extension_stack`, `effective_method`.

### `extension_add(name, position, purpose, status="stable", source="")`
- **Назначение:** добавить расширение в стек активной конфигурации.
- **⚠️ Директива:** `position` (1 = верх списка конфигуратора) и
  `purpose` (Исправление/Patch | Адаптация/Customization |
  Дополнение/Addition) ОБЯЗАТЕЛЬНЫ — спроси разработчика. Вызов без них
  — не ошибка, а подсказка с этим текстом.
- **Параметры:** `source`: "" — исходники уже на месте; "hub" —
  скопировать из EXT_HUB (/ext-dumps/<Имя>/); путь — из каталога.
  Отказ копии отменяет регистрацию.
- **Связанные:** `extension_move`, `extension_remove`.

### `extension_move(name, position)` / `extension_remove(name)`
- **Назначение:** сменить позицию расширения в списке конфигуратора
  (эффективный порядок пересчитывается внутри назначения) / убрать из
  стека (запись реестра; каталог ext/ и индекс не трогаются).
- **Связанные:** `extension_stack` (проверка после изменения).

### `extension_sync_from_ping(ping_result=None, cid="")`
- **Назначение:** сверить состав/версии расширений стека с «Пингом»
  обработки в живой базе. Расширения из базы сами НЕ добавляются
  (позиция и назначение — у разработчика). Без `ping_result` — Пинг по
  RUNTIME_URL; офлайн → подсказка собрать пакет
  `offline_submit([{"method": "ping"}])` и передать ответ параметром.
- **Связанные:** `extension_stack`.

### `effective_method(method, module_hint=None, include_dev=false)`
- **Назначение:** эффективный поток исполнения метода с учётом стека:
  [&Перед по убыванию] → body (база; пометка при «ИзменениеИКонтроль»)
  → [&После по возрастанию]; активный «Вместо» замещает body, прочие —
  shadowed-цепочка (ПродолжитьВызов).
- **Когда:** «что реально исполнится» — вместо чтения только базового
  кода.
- **Вердикты:** без стека — честный перечень перехватов без порядка
  (`order_confirmed: false`); notes о семантике (обрыв цепочки «Перед»
  при Отказ, безопасный режим).
- **Связанные:** `who_overrides`, `extension_map`, `read_function`.

## 7. Досье конфигурации

Двухслойная модель: детерминированный каркас из индекса (dossier.md) +
файлы-оверлеи владельца (notes-*.md — регенерация их не трогает).

### `build_docs(cid="")`
- **Назначение:** сгенерировать/обновить каркас досье из индекса
  (подсистемы → объекты → назначение → справка → точки входа).
  Перезаписывает dossier.md; notes-*.md не трогаются.
- **Вердикты:** `error` — нет конфигурации/индекса.
- **Связанные:** `get_docs`, `search_dossier`.

### `get_docs(cid="", section="")`
- **Назначение:** прочитать досье целиком или РАЗДЕЛ (подстрока
  заголовка «## …») + список оверлеев владельца.
- **Когда:** быстрый контекст по подсистеме; ⚠️ без `section` вернётся
  весь каркас — на крупной конфигурации он огромен (досье КА — десятки
  МБ), читай разделами.
- **Пример:** досье КА существует (собирается автоматически при
  пересборке индекса); раздел «Закупки» — компактная выжимка объектов
  подсистемы.
- **Связанные:** `search_dossier` (точечный поиск), `help_read`.

### `search_dossier(query, limit=20)`
- **Назначение:** подстроковый поиск по досье и заметкам владельца
  (notes-*.md), регистронезависимо; ответ {file, section, line, text}.
- **Пример:** `search_dossier("ТаможеннаяДекларацияИмпорт")` → строки в
  разделах «Закупки» и «ОбъектыМеждународные» dossier.md.
- **Связанные:** `get_docs`, `help_search`.

## 8. Конфигурации и индекс

### `config_list()`
- **Назначение:** реестр конфигураций: id, имена, версия релиза
  (config_info.Version), source_version (sha256-префикс), indexed_at,
  vectors, активная — первой.
- **Когда:** старт сессии — проверить, что активна та база; версия
  релиза имеет значение (КА 2.5.13 ≠ 2.5.22).
- **Пример:** активная `<config_id>` («КА 2.5 (рабочая)»,
  2.5.22.174, vectors 653 755), вторая — УТ 11.5.22.
- **Связанные:** `config_use`, `index_status`.

### `config_use(config_id)`
- **Назначение:** переключить конфигурацию ТЕКУЩЕГО КОНТЕКСТА (чат
  агента / панель — независимо); после смены — неблокирующий прогрев
  RAM-копии новой коллекции (выгрузка прежней → прогрев новой).
- **Когда:** целенаправленная работа с другой базой; НЕ переключай
  «на всякий случай» — чужие контексты привязаны к своим конфигурациям.
- **Связанные:** `config_list`, `semantic_status` (warm_state).

### `index_status()`
- **Назначение:** счётчики индекса активной конфигурации (methods,
  calls, object_attributes, predefined_items, enum_values…) из кэша
  реестра.
- **Пример:** КА: methods 653 756, calls 4 948 745, object_attributes
  80 587.
- **Связанные:** `index_freshness`, `rebuild_incremental`.

### `index_freshness(cid="")`
- **Назначение:** свежесть индекса: max(modules.mtime) против
  indexed_at.
- **Вердикты:** честное `unknown` на живых индексах — строитель mtime
  не заполняет (сверено с ddl.rs v0.1.20), возраст — по built_at /
  indexed_at; `stale` + lag — когда заработает сравнение.
- **Пример:** `{status: "unknown", built_at, indexed_at:
  "2026-11-15T20:09:18+00:00", modules_total: 23793}` + hint про
  `rebuild_incremental`.
- **Связанные:** `rebuild_incremental`.

### `rebuild_incremental(cid="")`
- **Назначение:** инкрементальная пересборка индекса: дифф выгрузки
  против modules (size/mtime), переиндексация только изменённых .bsl.
- **Вердикты:** честные refusal-ветки; новые файлы дифф не находит
  (их нет в modules), правки XML принимает только полная сборка.
- **Связанные:** `index_status`, `index_freshness`; полная пересборка —
  панель / POST /reindex (правило памяти для КА — в README).

### `semantic_status()` / `start_semantic_index()`
- **Назначение:** состояние семантического слоя (configured, модель,
  points, indexing, paused, warm_state warming/warm/cold) и запуск
  фоновой векторизации карточек методов.
- **Когда:** перед `codesearch` — жива ли векторная часть; после
  сборки/переключения конфигурации — warm_state.
- **Пример:** `{configured: true, points: 653755, warm_state: "warm",
  model: "qwen3-embedding-4b"}`.
- **Связанные:** `codesearch`, `config_use`, `semantic_mode`.

### `semantic_mode(config_id, mode, confirm=false)`
- **Назначение:** переключить режим семантики конфигурации в реестре:
  `full` — семантика включена; `fast` — выключена (честный отказ
  `codesearch`, сгрузка RAM-копии активной коллекции; точки в Qdrant
  сохраняются, повторное включение векторизации не требует).
- **Параметры:** `confirm` — разрешение на ПЛАТНУЮ векторизацию при
  переходе в `full`: без него меняется только флаг в реестре.
- **Когда:** экономить RAM/Qdrant на конфигурации, где семантика не
  нужна; вернуть обратно — быстро.
- **Связанные:** `semantic_status`, `start_semantic_index`.

## Рецепты (из боевых сессий)

### 1. Исследование незнакомой подсистемы
Дословно из боевой обратки (импортные закупки КА 2.5, ~15 вызовов —
полный ответ):

```
list_objects по корням слов («импорт», «таможенн»)
  → карта подсистемы за 2 вызова, включая константы-опции
    (= ответ на «где включить»)
→ object_overview / who_touches центрального объекта
  (регистраторы + читатели одним вызовом; измерения дают семантику
   связки: «ДокументПоступления: ПриобретениеТоваровУслуг», «НомерГТД»)
→ help_status → help_search на ЛЕКСИКЕ из карты (корни + префикс *)
  → help_read для точных страниц; mentions — мост дока → код
→ source_grep по телам — ТОЛЬКО для того, чего нет ни в индексе,
  ни в документации (условие попадания строк в регистр по ХО
  живёт в теле ManagerModule — индекс его не ищет)
```

### 2. Gap-анализ расширения (сверка контракта)
Проверка «что в расширении ↔ что в конфигурации» оракулами, без
чтения XML:

```
1. extension_stack / extension_map — что заимствовано/перехвачено
2. Список фактов о метаданных → check_claims БАТЧЕМ
   (kind=field с форматом «ТЧ.Колонка», kind=call для рёбер):
   боевая сессия — 61 claim за 3 вызова; два P0 ловились только так
3. Сомнительные хвосты: predefined_items по перечислениям/справочникам
   (поймал «ЮрАдресКонтрагента» vs «ЮридическийАдресКонтрагента»)
4. «holds: false» из оракула критичных фактов — перепроверь вторым
   способом (object_overview / predefined_details)
```

### 3. Поиск паттерна в коде (по телам)
Условие/литерал в теле — `code_grep` (тела залиты после полной сборки;
токенизация по словам) или `source_grep` (regex, вне индекса):

```
code_grep по имени/токену, если слово известно («Таможенн*»,
  «ЗначениеЗаполнено») — со сниппетом-подсветкой
→ regex-паттерн или подстрока внутри CamelCase-идентификатора:
  source_grep (regex до 200 симв., module_hint сужает обход,
  files_scanned показывает объём просмотра)
→ пустой результат — честный: скорректируй корень/регистр
  (ignorecase=true), а не ретраи тот же паттерн
→ нашёл файл/строку — read_function/read_module для тела
```

### 4. Изучение незнакомого объекта

```
object_overview (реквизиты, ТЧ, подсистемы, топ-методы)
→ repomap (сердце объекта: с чего начинать чтение)
→ read_function ключевых методов (тело + callers/callees)
→ verify_field для каждого факта, который пойдёт в вывод/код
```

### 5. «Как должно работать» vs «как сделано»
```
help_search на лексике предметной области (корни + «*»)
→ help_read — evidence штатного поведения; mentions → имена объектов
→ по этим именам: verify_field / read_function / source_grep —
   «как сделано» в этой базе
→ расхождение дока ↔ код — кандидат в доработку/баг:
   проверь опцию (list_objects по корню → константы-опции)
```
