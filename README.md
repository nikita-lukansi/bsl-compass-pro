# BSL Compass Pro

[![CI](https://github.com/nikita-lukansi/bsl-compass-pro/actions/workflows/ci.yml/badge.svg)](https://github.com/nikita-lukansi/bsl-compass-pro/actions/workflows/ci.yml)

MCP-сервер и веб-панель для ИИ-контура разработки 1С: структурная разведка
конфигураций (слой Rust для индексации), семантический поиск по коду (Qdrant),
живые данные из рабочих баз 1С (внешняя обработка «КомпасРантайм»; обезличивание
— только в офлайн-обмене, см. SECURITY.md),
корпус документации и заметок по конфигурации.

Лицензия — **AGPL-3.0** (текст: LICENSE.md, атрибуция: NOTICE.md).
Вопросы безопасности развертывания — SECURITY.md.

## Возможности

**Требование: Docker Desktop** — весь контур живёт в контейнере (образ
собирается rust + panel + runtime стейджами, без Docker не поднять).

- **Структурная разведка** (MCP-тулы поверх индекса): `verify_field`,
  `read_function`, `verify_call`, `repomap`, `triggers_on_write`,
  `object_overview`, карта расширений и стек перехватов — ответы о коде
  конфигурации без открытия конфигуратора;
- **Семантический поиск**: `codesearch` — вектор + буквальный через RRF
  по карточкам методов;
- **Живые данные 1С**: `data_query`, `records` (универсальная выборка
  с keyset-курсором), `document_movements`, `event_log` — только чтение,
  обезличивание per-chat, офлайн-конвейер через форму «Обмен» (файловый
  обмен без доработок конфигурации);
- **Панель**: обзор, реестр конфигураций, вкладка «Живые данные»,
  бэкапы, журнал вызовов, настройки;
- **Бэкапы**: слепок = индекс + манифест + снапшот Qdrant, inbox-восстановление.

Для агента: [docs/TOOLS.md](docs/TOOLS.md) — справочник всех MCP-тулов
(какой тул когда и как, честные границы, рецепты из боевых сессий);
[docs/EXPLORATION.md](docs/EXPLORATION.md) — как изучать незнакомую
конфигурацию (протокол доказательности, маршруты, анти-паттерны).

## Установка за две команды

Готовый образ публикуется в GHCR
(`ghcr.io/nikita-lukansi/bsl-compass-pro:latest`) — клонировать репозиторий
и собирать Rust-слой не нужно:

```bash
curl -O https://raw.githubusercontent.com/nikita-lukansi/bsl-compass-pro/main/docker-compose.yml
docker compose up -d    # панель: http://localhost:8240/ui · MCP: /mcp
```

`docker compose up` подтянет образ из GHCR (compose-файл знает и путь
сборки `build:` — он нужен только разработчикам, см. ниже). Пустой
контейнер стартует в bootstrap-режиме (панель-визард), `.env` не
обязателен. Если хотите задать настройки сразу (каталоги хабов,
`EMBEDDING_*`) — положите рядом файл `.env` ДО первого запуска:

```bash
curl -O https://raw.githubusercontent.com/nikita-lukansi/bsl-compass-pro/main/.env.example
mv -f .env.example .env   # и заполните нужное
```

иначе Docker создаст на месте `./.env` пустой каталог (маунт файла без
файла) — панель тогда честно подскажет «файла .env нет на хосте», а
каталог придётся удалить перед созданием файла. Обновление до свежего
образа — см. раздел [«Обновление»](#обновление).

### Развертывание из исходников

```bash
cp .env.example .env        # заполнить хабы/ключи (можно позже — старт и так поднимется)
docker compose build
docker compose up -d        # панель: http://localhost:8240/ui · MCP: /mcp
```

Что даёт «удобство»:
- пустой контейнер стартует в **bootstrap-режиме** (панель-визард), `.env` не обязателен для первого запуска;
- хаб-маунты `/dumps` — папки хоста, ничего не прячется в образе;
- данные (`/data`) и векторы (Qdrant) — в томмах, переживают пересоздание контейнера;
- порт только на `127.0.0.1`; мутации — за `ADMIN_TOKEN` (см. SECURITY.md);
- healthcheck встроен; обновление — см. раздел [«Обновление»](#обновление);
- полная пересборка крупной конфигурации — «правило памяти» из раздела
  [«Обновление»](#обновление) (останавливать qdrant).

Семантический слой включён в образ: при заданных `EMBEDDING_*` работает
`src/semantic/` (клиент эмбеддингов, Qdrant-хранилище, RRF-гибрид,
индексатор с возобновлением).

## Первый запуск: добавить конфигурацию

Компас разбирает конфигурацию по XML-выгрузке в файлы. Порядок первого
запуска (после `docker compose up -d`):

1. **Выгрузите конфигурацию в файлы.** В конфигураторе рабочей базы:
   «Конфигурация → Выгрузить конфигурацию в файлы…» и выберите каталог.
2. **Положите выгрузку в хаб дампов** — отдельным подкаталогом каталога
   `./dumps` рядом с compose-файлом (маунт `/dumps`, read-only),
   например `./dumps/KA25/`. В корне подкаталога должен лежать
   `Configuration.xml` — панель читает из него имя, версию и платформу и
   показывает их в списке выгрузок.
3. **Добавьте конфигурацию в панели:** вкладка «Конфигурации» → кнопка
   «Добавить». Мастер: алиас (отображаемое имя), краткое имя (входит в
   идентификатор `Compass_<краткое>_<uid>`), режим («Быстрый» — только
   SQLite-индекс; «Полный» — плюс Qdrant-векторы) и выбор выгрузки из
   найденных в хабе. Галка «Собрать индекс» запускает индексацию сразу
   после добавления; разделы мастера «Документация» и «Расширения» можно
   пропустить (вернуться к ним можно позже).
4. **Дождитесь сборки** — прогресс в карточке «Сборка индекса» на вкладке
   «Обзор»; по завершении MCP-тулы отвечают по новой конфигурации.

Крупные конфигурации (methods > 400k) при первой сборке тоже упираются в
память — «правило памяти» из раздела [«Обновление»](#обновление).

### Подключение агента

MCP-эндпоинт — `http://localhost:8240/mcp` (транспорт HTTP, тот же порт,
что и панель). Готовые снипеты с фактическим адресом — в панели:
«Настройки → Подключить агента». Минимальный конфиг для MCP-клиентов:

```json
{ "mcpServers": { "compass": { "url": "http://localhost:8240/mcp" } } }
```

Claude Code: `claude mcp add --transport http compass http://localhost:8240/mcp`.

## Обновление

**Готовый образ (GHCR):**

```bash
docker compose pull && docker compose up -d
```

**Из исходников:**

```bash
git pull
GIT_SHA=$(git rev-parse --short HEAD) docker compose build && docker compose up -d
```

Чек-лист после обновления: `curl http://127.0.0.1:8240/health` — git_sha из
ответа должен совпасть с текущим HEAD (`git rev-parse --short HEAD`). SHA
прошивается в образ при сборке (`ARG GIT_SHA`); без bake ответ отдаёт «dev».

**Правило памяти (полная пересборка крупной конфигурации).** Полная
пересборка крупной конфигурации (methods > 400k) — только при остановленном
qdrant: `docker stop bsl-compass-pro-qdrant` → пересборка (`/reindex`,
`python -m src.manage reindex <CID>` или `scripts/reindex.py reindex <CID>`)
→ после сборки `docker start bsl-compass-pro-qdrant`. Воркер сборки съедает
~3,5 ГиБ с пиком выше; вместе с qdrant (~2 ГиБ) лимит ВМ Docker Desktop
кончается — сборка умирает бесшумно (OOM уровня ВМ). Ядро отказывает
память-гардой с этой же подсказкой; семантика в окно сборки честно
недоступна. Первая сборка гардой не оценивается (ещё нет счётчиков) —
правило применяйте осознанно.

## Управление индексами вручную

Панельные сборки крупных конфигураций могут гибнуть по watchdog'у ядра;
`scripts/reindex.py` — постоянный обходной путь: тот же
отвязанный воркер gyrfalcon (как ручной nohup-прогон), после сборки —
тела методов в FTS, отметка в реестре и прогрев int8-коллекции. Запуск —
внутри контейнера, итог — JSON-отчёт в stdout, лог воркера —
`/data/system/logs/reindex_<cid>_<ts>.log` (путь есть в отчёте):

```bash
# пересобрать индекс существующей конфигурации
docker exec bsl-compass-pro python /app/scripts/reindex.py reindex <config_id>

# добавить НОВУЮ конфигурацию из хаба выгрузок (/dumps) и собрать
docker exec bsl-compass-pro python /app/scripts/reindex.py add KA25 --from-dumps KA25

# векторизация уже собранной конфигурации (тот же платный API — подтверждение)
docker exec bsl-compass-pro python /app/scripts/reindex.py vectorize <config_id> --yes-vectorize

# добавить расширение в стек АКТИВНОЙ конфигурации (копия из хаба EXT_HUB)
docker exec bsl-compass-pro python /app/scripts/reindex.py ext-add Экземпляр --position 1 --purpose Дополнение --source hub
```

- **Большие конфигурации (КА-размер, methods > 400k) — только при
  остановленном qdrant** («правило памяти» выше). На хосте:
  `docker stop bsl-compass-pro-qdrant`, затем запуск с подтверждением
  `--qdrant-stopped`; после сборки qdrant запускается обратно
  (`docker start bsl-compass-pro-qdrant`). Флаг `--stop-qdrant` сам qdrant
  не останавливает (docker CLI в образе нет) — печатает подсказку и
  завершается; продолжение — повторный запуск с `--qdrant-stopped`.
- Не запускайте параллельно с панельной сборкой — обе съедают память
  одного контейнера.
- `add` регистрирует конфигурацию в реестре, копирует выгрузку из `/dumps`
  в дом `/data/configs/<cid>/source` (после успешной сборки хост-дамп
  можно удалить) и делает новую конфигурацию активной — как панель.
- **Векторизация платная**: `add ... --vectorize` после сборки запускает
  фоновый прогон эмбеддингов (карточки методов — внешний API, оценка
  ≈ методы × 11 токенов). Требует подтверждения `--yes-vectorize`, без
  него скрипт откажется, ничего не тронув. Воркер не ждётся (отчёт
  «vectorization: started»), прогресс — в том же логе; панель этот прогон
  не показывает (отдельный процесс), кнопки паузы на него не действуют.
- **`vectorize <cid>`** — тот же отвязанный воркер, но для УЖЕ собранной
  конфигурации (без пересборки индекса): тот же платный API и то же
  подтверждение `--yes-vectorize`, лог —
  `/data/system/logs/vectorize_<cid>_<ts>.log`. По умолчанию скрипт не
  ждёт финала (минуты/часы); `--wait-warm [сек]` (без значения — потолок
  3600 с) поллит лог до финального отчёта воркера: `ok` + points из
  реестра либо честный `timeout` (воркер продолжает работать).
- **`ext-add <Имя> --position <N> --purpose <...> [--source hub|<путь>]`** —
  CLI-обёртка агентского тура `extension_add`: регистрирует расширение в
  стеке АКТИВНОЙ конфигурации и (с `--source`) копирует исходники — `hub`
  из хаба `EXT_HUB` (`/ext-dumps/<Имя>/`), значение-путь — из каталога;
  флаг без значения — исходники уже на месте. Позиция (1 = верх списка
  конфигуратора) и назначение (Исправление/Адаптация/Дополнение)
  обязательны. Индекс скрипт НЕ пересобирает — после добавления
  выполните `reindex <cid>` (подсказка есть в отчёте).

## Второй инстанс (параллельный контур)

docker-compose.yml жёстко фиксирует имена: контейнер `bsl-compass-pro`,
qdrant `bsl-compass-pro-qdrant`, образ
`ghcr.io/nikita-lukansi/bsl-compass-pro:latest`; имя
compose-проекта берётся из имени каталога. Клон репозитория в каталоге
с тем же именем при `docker compose up -d` **пересоздаст рабочий контейнер**
основного контура. Для второго инстанса изолируйте три вещи:

1. **Имя compose-проекта** — в `.env` клона (или флаг `-p`):
   `COMPOSE_PROJECT_NAME=compass-second`. Вместе с проектом изолируются
   и тома (`compass-second_compass-data` и т.д.) — данные не смешиваются.
2. **Имена контейнеров и образа** — `docker-compose.override.yml` в клоне
   с уникальными `container_name`/`image` (см. пример ниже) и своим
   хост-портом: `MCP_PORT=8241` в `.env` клона (внутри контейнера всегда
   8240, переменная меняет только хост-сторону маппинга).
3. **Тег образа** — ⚠️ `docker compose build` в клоне **перезапишет общий
   тег** `ghcr.io/nikita-lukansi/bsl-compass-pro:latest` образом из клона.
   Своё `image` в override
   нужно ДО первой сборки: перегенерированный старый образ сборщик мусора
   может вычистить, и вернуть тег назад без пересборки рабочего контура
   будет нечем.

Пример минимального override:

```yaml
services:
  compass:
    container_name: compass-second
    image: compass-second:latest
  qdrant:
    container_name: compass-second-qdrant
```

## Ресурсы и производительность

Живые замеры рабочего контура на выгрузке КА 2.5 (653k методов; «УТ» —
Управление торговлей 11). Раздел пополняется по мере новых замеров
(обновлено 2026-11-16).

| Что | Замер | Комментарий |
|---|---|---|
| Индекс КА | 653 756 методов, 4.95M рёбер calls, ~80k атрибутов | полная сборка |
| Полная пересборка УТ | 11 мин, пик памяти 1.28 ГиБ | можно при живом qdrant |
| Полная пересборка КА | 23 мин, пик памяти 3.5 ГиБ | только при остановленном qdrant — «правило памяти» выше |
| Qdrant RAM (int8, always_ram) | 1.65 ГиБ на 653k методов | формула: методы × 2560 dim × 1Б; оригиналы float32 лежат на диске — 6.2 ГиБ |
| Парковка конфигураций | пара (УТ+КА) ≈ 2.4 ГБ | сценарии объёма: ~10 ГБ на 15 конфигураций УТ-размера, ~27 ГБ на 15 КА-размера |
| codesearch | десятки мс после int8-квантизации; тёплый поиск 0.05 с | до неё: холодные запросы — десятки секунд, таймауты > 60 с; первый запрос после прогрева 2.73 с (разогрев путей) |
| callers / resolve_callee / repomap | суффиксный индекс по срезу calls | план запроса проверен EXPLAIN QUERY PLAN |
| warm-up always_ram при переключении конфигурации | выгрузка прежней 0.26 с, прогрев новой 0.46 с | авто при `config_use`: always_ram=true только активной; пересборки квантованных нет — Qdrant мапит готовые, смена конфигурации семантически незаметна (<1 с) |

## Рантайм-контур 1С (живые данные)

Живые данные из рабочей базы — через внешнюю обработку **«КомпасРантайм»**.

**Где взять.** Исходники обработки (.bsl + формы) — в репозитории проекта,
`blocks/runtime/src/`; там же лежит собранный `blocks/runtime/КомпасРантайм.epf`.
Пересборка .epf из исходников — конфигуратором: «Файл → Открыть» →
корневой XML обработки (`blocks/runtime/src/КомпасРантайм.xml`), затем
«Файл → Сохранить как» в `.epf`.

**Онлайн-режим.** Обработка запускается в базе как HTTP-сервис
(`RUNTIME_URL` в `.env`); ядро вызывает её напрямую, состояние контура —
тул `runtime_status`.

**Офлайн-режим** (`RUNTIME_MODE=offline`) — файловый обмен без публикации
базы, каталог задаётся `OFFLINE_HUB` (дефолт `./offline` на хосте, внутри
контейнера — `/data/system/offline`):

1. агент собирает пакет `offline_submit([...])` → в каталоге обмена
   появляется заявка `queue/req_<id>.json`;
2. оператор открывает обработку в базе (Файл → Открыть; флажок безопасного
   режима снять) → форма «Обмен»: указать папку запросов и папку
   результатов (каталог обмена из шага 1 — `queue/` и `results/`), затем
   «Запустить» (очередь с автоповтором) или «Выполнить сейчас» (разово).
   Исполняются только read-only SELECT (мутирующие ключевые слова —
   блок-лист); обработанная заявка помечается `.done`, ответ пишется
   `results/resp_<id>.json`;
3. watcher ядра подхватывает ответ; агент дожидается его
   `offline_wait(task_id)`.

Ядро ходит в базу под пользователем «только чтение», RLS действует.
Обезличивание: per-chat словарь токенов, деанонимизация только на выдаче
человеку в панели; сырой архив — `ARCHIVE_RAW=off` отключает (детали —
SECURITY.md).

## Разработка

Python **3.12**. Установка зависимостей (рантайм + dev):

```bash
pip install -r requirements.txt -r requirements-dev.txt
python -m pytest tests/ -q          # герметичные тесты (локальный Qdrant для семантики)
cd panel && npm ci && npm run build # панель
docker compose build                # образ собирает rust + panel + runtime стейджами
```
